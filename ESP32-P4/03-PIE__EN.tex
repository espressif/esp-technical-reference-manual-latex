\chapter{Processor Instruction Extensions (PIE)}
\label{mod:pie}




\section{Overview}

The \chipname{} HP 32-bit RISC-V dual-core processor supports standard RV32IMAFCZc extensions, and it also contains a custom extension named Xesploop(hardware loop) which enables execution of ‘for’ loops in hardware to improve performance. For more details, please refer to the \ref{mod:riscvcpu}\nameref{mod:riscvcpu} chapter. Furthermore, a custom AI and DSP extension, Xespv2p1, is provided to improve the efficiency of specific AI and DSP algorithms.


This chapter introduces the details of Xespv2p1 extension, which is based on the SIMD (Single Instruction Multiple Data) architecture. It supports 8-bit, 16-bit, and 32-bit vector operations, significantly improving data throughput. In addition, arithmetic instructions such as multiplication, shifting, and accumulation, can perform data operations and transfer data at the same time, further enhancing the instruction execution efficiency.

\section{Features}

The Xespv2p1 extension has the following features:

\begin{itemize}
    \item 128-bit general-purpose registers
    \item 128-bit vector operations, e.g., multiplication, addition, subtraction, accumulation, shifting, and comparison
    \item Integration of data transfer into arithmetic instructions
    \item Support for non-aligned 128-bit vector data
    \item Configurable rounding and saturation modes

\end{itemize}

The Xespv2p1 unit contains:

\begin{itemize}
    \item Address unit that reads 8/16/32/64/128-bit aligned data
    \item Bank of eight 128-bit vector QR registers

    \begin{itemize}

    \item XACC: 40-bit accumulator
\end{itemize}

\subsection{Vector Registers}
Xespv2p1 provides eight 128-bit wide vector registers (QR). Each register can be represented as an array of sixteen 8-bit data elements, an array of eight 16-bit data elements, or an array of four 32-bit data elements. The 8-bit, 16-bit, or 32-bit format will be chosen according to the instruction being executed. 

\subsection{Arithmetic Logic Unit (ALU)}

The Arithmetic Logic Unit (ALU) can operate as an 8-bit, 16-bit, or 32-bit ALU, depending on the input data width. That is, it works as an 8-bit ALU for 8-bit input data, as a 16-bit ALU for 16-bit input data, and as a 32-bit ALU for 32-bit input data. It performs arithmetic operations such as addition and subtraction, and bitwise operations such as AND, OR, and shift.\\
The input for ALU operations comes from QR registers. The result of the operations can be saved in the QR registers.

\subsection{Multiply-and-Accumulate (MAC) Unit}
The multiply-and-accumulate (MAC) unit performs multiply-and-accumulate operations. The MAC unit includes eight 16-bit multipliers and sixteen 8-bit multipliers. The results of MAC operations are stored in the special accumulator registers, i.e., XACC and QACC.

\subsubsection{QACC Accumulator Register}

The QACC accumulator register is used for saving sixteen 8-bit MAC results or eight 16-bit MAC results. It is divided into two parts: 256-bit QACC\_H and 256-bit QACC\_L. In the case of 8-bit MAC operations, each of the two 256-bit QACC registers is represented as eight 32-bit elements, while in the case of 16-bit MAC operations, they are represented as four 64-bit elements.

To store the accumulator result in the QR registers, the 32-bit result can be converted to 8 bits by right-shifting. For 16-bit MAC operations, the 64-bit result can be converted to 16 bits by right-shifting.

Data can be loaded from memory into the QACC register. The initial value can be reset to 0.

\subsubsection{XACC Accumulator Register}

The XACC register is a 40-bit accumulator; its purpose is to store the sum of all multipliers' output results.\\
It is possible to load data from memory to XACC or reset the initial value to 0.

\subsection{Address Unit}

Most of the instructions in Xespv2p1 allow loading or storing data from/to the 128-bit Q registers in parallel. The address unit provides functionality for parallel manipulation of address registers, saving the time needed to update address registers.\\
It is possible to perform address register operations like AR + signed immediate, ARx + ARy, and AR + 16.

\subsubsection{General-Purpose Registers}
\paragraph{AR}


Although there are 32 general-purpose registers in the HP core, only 16 of these registers are available for the Xespv2p1 extension instructions: x8-x15 and x24-x31 (s0-s1, a0-a5, s8-s11, t3-t6).



\subsubsection{Vector Registers}

\paragraph{QR}

The general purpose registers are only 32-bit wide, while \chipname{} can access 128-bit data at a time, so they can only use a quarter of the bandwidth capacity of the existing data bus. For this reason, \chipname{} has added eight 128-bit customized vector registers, i.e., QR registers. QR registers are mainly used to store the data acquired/used by the 128-bit data bus to read or write memory, as well as to temporarily store the operation results generated from 128-bit data operations.

As the processor executes instructions, an individual QR register is treated as sixteen 8-bit, eight 16-bit, or four 32-bit operands depending on the vector operation bit width defined by the instruction, thus enabling a single instruction to perform operations on multiple operands.

When using vector register as operands in instructions, you need to explicitly declare the number of the assigned register. For example:

\begin{center}
$\hyperref[instruction:ESPVADDS8]{ESP.VADD.S8} \hspace{1em} q2, q0, q1$
\end{center}

This instruction uses No.0 and No.1 QR registers as input vectors and stores the vector addition result in the No.2 QR register.

\subsubsection{Special Registers}
\label{sec:pie-spec-reg}

Contrary to general-purpose registers, special registers are used implicitly by certain instructions. Therefore, you do not need to and cannot specify them as operands in the instructions. For example:

\begin{center}
    $\hyperref[instruction:ESPVMULS16]{ESP.VMUL.S16}\hspace{1em}q2, q0, q1$
\end{center}

This vector multiplication instruction uses q0 and q1 custom vector registers as inputs. During the internal operation, the intermediate 32-bit multiplication result is shifted to the right, and then the lower 16-bit of the result is retained to form a 128-bit output to q2. The shift amount in the process is determined by the value in the Shift Amount Register (SAR) and this SAR register will not appear in the instruction operand list.


\paragraph{Shift Amount Register (SAR)}
The Shift Amount Register (SAR) stores the shift value in bits. There are two types of instructions in \chipname{}'s extended instruction set that use SAR: the type of instructions to shift vector data, including \hyperref[instruction:ESPVSRS32]{ESP.VSR.S32} and \hyperref[instruction:ESPVSL32]{ESP.VSL.32}, and the multiplication instructions, including ESP.VMUL.*, ESP.CMUL.*, ESP.FFT.AMS.* and ESP.FFT.CMUL.*.

The first type uses the lower 5 bits of SAR as the right-shift value and the left-shift value respectively, while the latter type uses the value for the right shift of the intermediate multiplication result, which determines the accuracy of the final result.

\paragraph{SAR\_BYTE}

The SAR\_BYTE stores the shift value in bytes. This special register is designed to handle the non-aligned 128-bit data (see Section \ref{sec:pie-data-align}). For vector arithmetic instructions, the data read or stored by extended instructions are forced to be 16-byte aligned, but in practice, there is no guarantee that the data addresses used are always 16-byte aligned.

\hyperref[instruction:ESPLD128USARIP]{ESP.LD.128.USAR.IP} and \hyperref[instruction:ESPLD128USARXP]{ESP.LD.128.USAR.XP} instructions write the lower 4-bit values of the memory access register that represent non-aligned data to SAR\_BYTE while reading 128-bit data from memory.

There are two types of instruction in \chipname{}'s extended instruction set that use SAR\_BYTE. One is dedicated to handling non-aligned data in QR registers, including ESP.SRCQ.* and ESP.SRC.Q*. These instructions read two 16-byte data from two aligned addresses, before and after the non-aligned address, put them together, and then shift it by the byte size stored in SAR\_BYTE to get a 128-bit data from the non-aligned address. The other type of instruction handles non-aligned data while executing arithmetic operations, which usually has a suffix of ``.QUP".





\paragraph{FFT\_BIT\_WIDTH}

This special register is dedicated to the \hyperref[instruction:ESPBITREV]{ESP.BITREV} instruction. The value inside this register indicates the operating mode of \hyperref[instruction:ESPBITREV]{ESP.BITREV}. It ranges from 0 \verb+~+ 7, indicating 3-bit \verb+~+ 10-bit operating mode respectively. For more details, please refer to instruction \hyperref[instruction:ESPBITREV]{ESP.BITREV}.

\paragraph{UA\_STATE}

This special register is dedicated to the \hyperref[instruction:ESPFFTAMSS16LDINCPUAUP]{ESP.FFT.AMS.S16.LD.INCP.UAUP} instruction. It stores the non-aligned 128-bit data read from memory. Each time when this instruction is called, the data in this register is concatenated to the newly read non-aligned data, and then the result is shifted to produce a 128-bit aligned output.

\subsection{Misalignment Handling}

\chipname{} HP core Xespv2p1 misaligned load/store has 2 configurable modes via \hyperref[mis_ld]{mis\_ld} and \hyperref[mis_st]{mis\_st}:
\begin{itemize}
    \item 0: Force alignment mode
    \item 1: Hardware misaligned mode
\end{itemize}



\subsubsection{Force alignment mode}
In this mode, all access addresses in the extended instruction set are forced to be aligned, i.e., the lowest bits will be replaced by 0. For example, if a read operation is initiated for 128-bit data at 0x3fc8\_0024, the lowest 4-bit of this access address will be forced to be set to 0. Eventually, the 128-bit data stored at 0x3fc8\_0020 will be read. Similarly, the lowest 3-bit of the access address for 64-bit data will be set to 0; the lowest 2-bit of the access address for 32-bit data will be set to 0; the lowest 1-bit of the access address for 16-bit data will be set to 0.

The above design requires aligned addresses of the access operations initiated. Otherwise, the data read will not be what you expected. In application code, you need to explicitly declare the alignment of the variable or array in memory. 16-byte alignment can meet the needs of most application scenarios.


Since the memory address of the data involved in some operations is uncertain in specific application scenarios, this extended instruction set provides a special register SAR\_BYTE and related instructions such as ESP.LD.128.USAR.* and ESP.SRC.*, to handle non-aligned data.

Assume that the 128-bit non-aligned data address is stored in the general-purpose register a8. This 128-bit data can be read into the specified QR register (q2 in the following example) by the following code:\\
$ \hyperref[instruction:ESPLD128USARIP]{ESP.LD.128.USAR.IP}\hspace{1cm}q0,\hspace{0.5cm}a8,\hspace{0.5cm}16 $ \\
$ \hyperref[instruction:ESPVLD128IP]{ESP.VLD.128.IP}\hspace{1cm}q1,\hspace{0.5cm}a8,\hspace{0.5cm}16 $ \\
$ \hyperref[instruction:ESPSRCQ]{ESP.SRC.Q}\hspace{1cm}q2,\hspace{0.5cm}q0,\hspace{0.5cm}q1 $

\subsubsection{Hardware misaligned mode}

In this mode, hardware automatically handles misaligned accesses, splitting them into multiple aligned accesses. The results of these accesses always meet your expectations.

\subsection{Data Overflow and Saturation Handling}

Data overflow means that the size of the operation result exceeds the maximum value that can be stored in the result register. Take the \hyperref[instruction:ESPVMULS8]{ESP.VMUL.S8} instruction as an example, the result of two 8-bit multipliers is 16-bit, and it should still be 16-bit after right-shifting. However, the final result will be stored in the 8-bit register, which may cause the risk of data overflow.

In the design of the \chipname{}'s instruction extensions, there are two ways to handle data overflow, namely saturation and wraparound (keeping only the lower significant bits). The former controls the calculation result according to the range of values that can be stored in the result register. If the result exceeds the maximum value of the result register, take the maximum value; if the result is smaller than the minimum value of the result register, take the minimum value. This approach will be explicitly indicated in the instruction descriptions. For example, the ESP.VADDS.* instructions perform saturation on the results of addition operations. For the data overflow handling of internal calculation results in other instructions, the wraparound approach is used, i.e., only the lower bits matching the bit width of the result register are retained and stored in the result register.


There is a 1-bit status register \hyperref[vxsat]{vxsat} which indicates whether overflow or underflow happened in the last calculation (the precondition is that \hyperref[vxsat_en]{vxsat\_en} is set). This bit is cleared automatically when the \hyperref[regdesc:ESPCFG]{CFG} register is read.

\subsection{Arithmetic Instructions}
\label{sec:pie-arithmetic-instructions}

Arithmetic instructions mainly use the SIMD (Single Instruction Multiple Data) principle for vector data operations, including vector addition, vector multiplication, vector complex multiplication, vector multiplication accumulation, vector and scalar multiplication accumulation, etc.

\subsubsection{Vector Addition Instructions}

\chipname{} provides vector addition and subtraction instructions for data in 1-byte, 2-byte and 4-byte units.

Considering that the input and output operands required for vector operations are stored in memory, in order to reduce extra operations as reading memory and to improve the speed of code execution, vector addition instructions are designed to perform the addition and the 16-byte access at the same time, and the value in the address register is increased by 16 after the access, thus directly pointing to the next continuous 16-byte memory address. You can select the appropriate instruction according to the actual algorithm needs.

In addition, vector addition instructions also saturate the result of addition and subtraction to ensure the accuracy of arithmetic operations.

In order to reduce extra operations as reading memory and improve the speed of code execution, vector multiplication accumulation instructions are designed to perform the multiplication accumulation and access 16 bytes at the same time. \subsection{Comparison Instructions}
\label{sec:pie-comparison-instructions}

Vector comparison instructions compare data in the unit of 1 byte, 2 bytes, or 4 bytes, including the instructions that take the larger/smaller one between the two compared values, that set all bits to 1 when the two values are equal and to 0 otherwise, that set all bits to 1 when the former value is larger than the latter and otherwise set them to 0, and that set all bits to 1 when the former value is smaller than the latter and otherwise set them to 0.

Considering that the input and output operands required for vector operations are stored in memory, to reduce extra operations like memory reads and improve code execution speed, vector operations are performed together with memory access to 16-byte addresses. After each access, the address is incremented by 16, directly pointing to the next 16-byte memory block. The appropriate instruction can be selected based on the actual needs.

\section{Instruction Performance}\label{subsec:pie_pipeline}
For processors designed based on a pipeline, it is ideal that CPU issues one instruction onto the pipeline per processor cycle. The \chipname{} processor adopts the 5-stage pipeline technology: F (instruction fetch), D (decode), E (execute), M (memory access), and W (write back). Table \ref{tab:pie_processor_5stage} shows what the processor does at each pipeline stage.\\

\begin{longtable}[c]{|l|c|l|}
    \caption{Five-Stage Pipeline of \chipname{} Processor}
    \label{tab:pie_processor_5stage}\\
    \hline
    \rowcolor{lightgray}
    \textbf{Pipeline Stage} & \textbf{Number} & \textbf{Operation} \\\hline
    F & - & Fetch instructions\\\hline
    D & 0 & \makecell[l]{Read the general-purpose registers AR and QR\\Decode instructions, detect interlocks, and forward operands}\\\hline
    E & 1 & \makecell[l]{For arithmetic instructions, the ALU (addition, subtraction, multiplication, etc.) works\\For read memory instructions, generate virtual addresses for memory access\\For branch jump instructions, select jump addresses}\\\hline
    M & 2 & Issue read and write memory accesses \\\hline
    W & 3 & Write back to registers the calculated results and the data read from memory\\\hline
\end{longtable}

The processor cannot issue an instruction to the pipeline until all the operands and hardware resources required for the operation are ready. However, there are the following hazards in the actual program running process, which can cause stopped pipeline and delayed implementation of instructions.

\subsection{Data Hazard}
When instruction A writes the result to register X (including explicit general-purpose registers and implicit special registers), and instruction B needs to use the same register as an input operand, this case is referred to as that instruction B depends on instruction A. If instruction A prepares the result to be written to register X at the end of the SA pipeline stage, and instruction B reads the data in register X at the beginning of the SB pipeline stage, then instruction A must be issued $D = max(SA - SB + 1, 0)$ cycles before instruction B.\\
If the processor fetches instruction B less than D cycles after instruction A, the processor delays issuing instruction B until D cycles have passed. The act of the processor delaying an instruction because of pipeline interactions is called an interlock.\\
Suppose the SA pipeline stage of instruction A is W, and the SB pipeline stage of instruction B is E. Instruction B is issued to the pipeline $D = max(2 - 1 + 1, 0) = 2$ cycles later than instruction A, as shown in Figure \ref{fig:pie_data_hazard}.\\
When the output operand of an instruction is designed to be available at the end of a pipeline stage, it means that the operation of the instruction is over. Usually, instructions that depend on this result data must wait until the output operand is written to the corresponding register before retrieving it from the corresponding register. The processor supports the "bypass" operation. It detects when the input operand of an instruction is generated at which pipeline stage of the instruction and does not need to wait for the data to be written to the register. It can directly forward the data from the pipeline stage where it is generated to the stage where it is needed.

\begin{figure}[H]
    \centering
    \fbox{\includegraphics[width=0.9\textwidth]{\modulefiles/figures/data_hazard__EN}}
    \caption{Interlock Caused by Instruction Operand Dependency}
    \label{fig:pie_data_hazard}
\end{figure}

Data dependencies between instructions are determined by the dependencies between operands and the pipeline stages at which reads and writes happen. Section \ref{sec:pie-instruction-descrip} lists all the read-write stages of all operands for each instruction. 


\subsection{Hardware Resource Hazard}
When multiple instructions call the same hardware resource at the same time, the processor allows only one of the instructions to occupy the hardware resource, and the rest of them will be delayed. For example, there are only eight 16-bit multipliers in the processor; instruction C requires eight of them in pipeline stage M, and instruction D requires four of them in pipeline stage E. As shown in Figure \ref{fig:pie_resource_hazard}, instruction C is issued in cycle T+0, and instruction D is issued in cycle T+1, so four multipliers are applied to be occupied simultaneously in cycle T+3; at this time, the processor will delay the issue of instruction D into the pipeline by one cycle to avoid conflict with instruction C.

\begin{figure}[H]
    \centering
    \fbox{\includegraphics[width=0.9\textwidth]{\modulefiles/figures/resource_hazard__EN}}
    \caption{Hardware Resource Hazard}
    \label{fig:pie_resource_hazard}
\end{figure}

\subsection{Control Hazard}
Data and hardware resource hazards can be mitigated by reordering the code, but control hazards are difficult to optimize. Program code usually has many conditional select statements, which determine the execution path based on whether certain conditions are met. The compiler translates the conditional statements into branch and jump instructions: if the condition is true, it jumps to a target address to execute the corresponding code; otherwise, the subsequent instructions are executed. When the conditions are met, as shown in Figure \ref{fig:pie_control_hazard}, the processor re-fetches instructions from the new target address. At this point, the instructions currently in the F and D stages of the pipeline are discarded, which means the pipeline remains stagnant for 2 cycles.\\
