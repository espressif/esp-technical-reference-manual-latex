\chapter{Processor Instruction Extensions (PIE)}
\label{mod:pie}

\section{Overview}

The \chipname{} HP 32-bit RISC-V dual-core processor supports the standard RV32IMAFCZcZb extensions. It also includes a custom extension named Xesploop (hardware loop), which executes ``for'' loops in hardware to improve performance. For more details, see the \ref{mod:riscvcpu}\nameref{mod:riscvcpu} chapter. In addition, a custom AI and DSP extension, Xespv2p2, accelerates selected AI and DSP algorithms.


This chapter describes the Xespv2p2 extension, which is based on the SIMD (Single Instruction Multiple Data) architecture. It supports 8-bit, 16-bit, and 32-bit vector operations, which improves data throughput. Arithmetic instructions such as multiplication, shifting, and accumulation can also transfer data while performing computation, further improving execution efficiency.

\section{Features}

The Xespv2p2 extension has the following features:

\begin{itemize}
    \item 128-bit general-purpose registers
    \item 128-bit vector operations, e.g., multiplication, addition, subtraction, accumulation, shifting, and comparison
    \item Integration of data transfer into arithmetic instructions
    \item Support for non-aligned 128-bit vector data
    \item Configurable rounding and saturation modes

\end{itemize}

The Xespv2p2 unit contains:

\begin{itemize}
    \item An address unit that reads 8/16/32/64/128-bit aligned data
    \item A bank of eight 128-bit vector QR registers
    \item An arithmetic logic unit (ALU) with
    \begin{itemize}
        \item sixteen 8-bit multipliers
        \item eight 16-bit multipliers
    \end{itemize}
    \item QACC\_H/QACC\_L: two 256-bit accumulators
    \item XACC: a 40-bit accumulator
\end{itemize}

\subsection{Vector Register Bank}
Xespv2p2 provides eight 128-bit vector registers (QR). Each register can be viewed as an array of sixteen 8-bit elements, eight 16-bit elements, or four 32-bit elements. The element width depends on the instruction being executed. 

\subsection{Arithmetic Logic Unit (ALU)}

The ALU can operate on 8-bit, 16-bit, or 32-bit data, matching the input width: an 8-bit ALU for 8-bit inputs, a 16-bit ALU for 16-bit inputs, and a 32-bit ALU for 32-bit inputs. It performs arithmetic operations such as addition and subtraction, and bitwise operations such as AND, OR, and shift.\\
ALU operands come from QR registers, and results can be written back to QR registers.

\subsection{Multiply-and-Accumulate (MAC) Unit}
The multiply-accumulate (MAC) unit performs MAC operations. It includes eight 16-bit multipliers and sixteen 8-bit multipliers. MAC results are stored in the special accumulator registers XACC and QACC.

\subsubsection{QACC Accumulator Register}

The QACC accumulator stores sixteen 8-bit MAC results or eight 16-bit MAC results. It consists of two parts: 256-bit QACC\_H and 256-bit QACC\_L. For 8-bit MAC operations, each 256-bit QACC register is treated as eight 32-bit elements. For 16-bit MAC operations, each is treated as four 64-bit elements.

To write an accumulator result back to a QR register, a 32-bit result can be reduced to 8 bits by right-shifting. For 16-bit MAC operations, a 64-bit result can be reduced to 16 bits by right-shifting.

Data can be loaded from memory into QACC, or QACC can be cleared to 0.

\subsubsection{XACC Accumulator Register}

XACC is a 40-bit accumulator that stores the sum of all multiplier outputs.\\
Data can be loaded from memory into XACC, or XACC can be cleared to 0.

\subsection{Address Unit}

Most Xespv2p2 instructions can load from or store to the 128-bit QR registers in parallel with computation. The address unit updates address registers in parallel, reducing the cost of explicit address updates.\\
Supported address updates include AR + signed immediate, ARx + ARy, and AR + 16.

This section describes the registers used by the \chipname{} extended instruction set. 
See Table \ref{tab:pie-regs-list} for a register summary.

\subsubsection{General-Purpose Registers}
\paragraph{AR}


Although the HP core has 32 general-purpose registers, only 16 of them are available to Xespv2p2 extension instructions: x8–x15 and x24–x31 (s0–s1, a0–a5, s8–s11, t3–t6).



\subsubsection{Vector Registers}

\paragraph{QR}

General-purpose registers are only 32 bits wide, while \chipname{} can access 128-bit data at a time, so they use only a quarter of the available data-bus bandwidth. For this reason, \chipname{} provides eight 128-bit vector registers (QR). QR registers mainly hold data transferred over the 128-bit bus for memory load and store, and temporary results of 128-bit vector operations.

During instruction execution, a QR register is treated as sixteen 8-bit, eight 16-bit, or four 32-bit operands, depending on the vector width defined by the instruction, so that one instruction can operate on multiple elements.

When a QR register is used as an instruction operand, you must specify its index explicitly. For example:

\begin{center}
$\hyperref[instruction:ESPVADDS8]{ESP.VADD.S8} \hspace{1em} q2, q0, q1$
\end{center}

This instruction uses QR registers q0 and q1 as inputs and stores the vector addition result in q2.

\subsubsection{Special Registers}
\label{sec:pie-spec-reg}

Unlike general-purpose registers, special registers are used implicitly by certain instructions. You neither need to nor can specify them as instruction operands. For example:

\begin{center}
    $\hyperref[instruction:ESPVMULS16]{ESP.VMUL.S16}\hspace{1em}q2, q0, q1$
\end{center}

This vector multiplication uses q0 and q1 as inputs. Internally, each intermediate 32-bit product is right-shifted, and the lower 16 bits are retained to form the 128-bit result written to q2. The shift amount comes from the Shift Amount Register (SAR), which does not appear in the instruction operand list.


\paragraph{SAR}
The Shift Amount Register (SAR) stores the shift amount in bits. Two classes of \chipname{} extension instructions use SAR: vector shift instructions, including \hyperref[instruction:ESPVSRS32]{ESP.VSR.S32}, \hyperref[instruction:ESPVSLS32]{ESP.VSL.S32}, and \hyperref[instruction:ESPVSLU32]{ESP.VSL.U32}; and multiplication-related instructions, including ESP.VMUL.*, ESP.CMUL.*, ESP.FFT.AMS.*, and ESP.FFT.CMUL.*.

Vector shift instructions use the lower 5 bits of SAR as the right-shift or left-shift amount. Multiplication-related instructions use SAR to right-shift intermediate products, which affects the precision of the final result.

\paragraph{SAR\_BYTE}

SAR\_BYTE stores the shift amount in bytes. It is used to handle misaligned 128-bit data (see Section \ref{sec:pie-data-align}). For vector arithmetic instructions, loads and stores are forced to 16-byte alignment, but application data addresses are not always 16-byte aligned.

While loading 128-bit data from memory, \hyperref[instruction:ESPLD128USARIP]{ESP.LD.128.USAR.IP} and \hyperref[instruction:ESPLD128USARXP]{ESP.LD.128.USAR.XP} write the lower 4 bits of the access address (the misalignment offset) to SAR\_BYTE.

Two classes of \chipname{} extension instructions use SAR\_BYTE. The first handles misaligned data in QR registers and includes ESP.SRCQ.* and ESP.SRC.Q*. These instructions load two 16-byte blocks from the aligned addresses before and after the misaligned address, concatenate them, and right-shift by the byte count in SAR\_BYTE to obtain 128-bit data at the misaligned address. The second class handles misalignment during arithmetic and usually has the ``.QUP'' suffix.





\paragraph{FFT\_BIT\_WIDTH}

This special register is used only by \hyperref[instruction:ESPFFTBITREV]{ESP.FFT.BITREV}. Its value selects the operating mode of \hyperref[instruction:ESPFFTBITREV]{ESP.FFT.BITREV}: 0 through 7 correspond to 3-bit through 10-bit modes. For details, see \hyperref[instruction:ESPFFTBITREV]{ESP.FFT.BITREV}.

\paragraph{UA\_STATE}

This special register is used only by \hyperref[instruction:ESPFFTAMSS16LDINCPUAUP]{ESP.FFT.AMS.S16.LD.INCP.UAUP}. It holds misaligned 128-bit data previously read from memory. Each time the instruction runs, the contents of this register are concatenated with newly loaded misaligned data and then shifted to produce a 128-bit aligned result.

\subsection{Misaligned Access Handling}

Misaligned load and store for the \chipname{} HP core Xespv2p2 extension can be configured through \hyperref[mis_ld]{mis\_ld} and \hyperref[mis_st]{mis\_st}:
\begin{itemize}
    \item 0: Force-alignment mode
    \item 1: Hardware misaligned mode
\end{itemize}



\subsubsection{Force-alignment mode}
In this mode, every access address used by the extended instruction set is forced into alignment by clearing its lowest bits. For example, a 128-bit load from 0x3fc8\_0024 forces the lowest 4 bits to 0, so the data at 0x3fc8\_0020 is read. Likewise, the lowest 3 bits are cleared for 64-bit accesses, the lowest 2 bits for 32-bit accesses, and the lowest 1 bit for 16-bit accesses.

Therefore, access addresses must be correctly aligned; otherwise the returned data is not what you expect. In application code, declare the required alignment for variables or arrays. 16-byte alignment covers most use cases.


When the address of data used in an operation is not known to be aligned, the extension provides SAR\_BYTE and related instructions such as ESP.LD.128.USAR.* and ESP.SRC.* to reconstruct misaligned 128-bit data.

Assume that register a8 holds the address of misaligned 128-bit data. The following sequence loads that data into QR register q2:\\
$ \hyperref[instruction:ESPLD128USARIP]{ESP.LD.128.USAR.IP}\hspace{1cm}q0,\hspace{0.5cm}a8,\hspace{0.5cm}16 $ \\
$ \hyperref[instruction:ESPVLD128IP]{ESP.VLD.128.IP}\hspace{1cm}q1,\hspace{0.5cm}a8,\hspace{0.5cm}16 $ \\
$ \hyperref[instruction:ESPSRCQ]{ESP.SRC.Q}\hspace{1cm}q2,\hspace{0.5cm}q0,\hspace{0.5cm}q1 $

\subsubsection{Hardware misaligned mode}

In this mode, hardware automatically handles misaligned accesses by splitting them into multiple aligned accesses. The results match the expected data.

\subsection{Data Overflow and Saturation}

Data overflow occurs when a result does not fit in the destination register. For example, in \hyperref[instruction:ESPVMULS8]{ESP.VMUL.S8}, each product of two 8-bit values is 16 bits wide and remains 16 bits after a right shift, but the final storage width is 8 bits, so overflow is possible.

The \chipname{} extensions handle overflow in two ways: saturation and wraparound (retaining only the lower bits). Saturation clamps the result to the minimum or maximum value representable in the destination. Instructions that use saturation state this explicitly—for example, ESP.VADDS.* saturates addition results. Other internal overflow cases use wraparound: only the lower bits that fit the destination width are kept.


The 1-bit status flag \hyperref[vxsat]{vxsat} indicates whether saturation occurred in the last operation (only when \hyperref[vxsat_en]{vxsat\_en} is set). Reading the \hyperref[regdesc:ESPCFG]{CFG} register clears this bit.

\subsection{Arithmetic Instructions}
\label{sec:pie-arithmetic-instructions}

Arithmetic instructions perform SIMD vector operations, including vector addition, multiplication, complex multiplication, multiply-accumulate, and vector–scalar multiply-accumulate.

\subsubsection{Vector Addition Instructions}

\chipname{} provides vector addition and subtraction instructions for 1-byte, 2-byte, and 4-byte elements.

These instructions also saturate addition and subtraction results to preserve numeric range.

\section{Instruction Performance}\label{subsec:pie_pipeline}
On a pipelined processor, the ideal case is to issue one instruction per cycle. The \chipname{} processor uses a five-stage pipeline: F (fetch), D (decode), E (execute), M (memory), and W (write-back). Table \ref{tab:pie_processor_5stage} summarizes each stage.\\

\begin{longtable}[c]{|l|c|l|}
    \caption{Five-Stage Pipeline of the \chipname{} Processor}
    \label{tab:pie_processor_5stage}\\
    \hline
    \rowcolor{lightgray}
    \textbf{Pipeline Stage} & \textbf{Number} & \textbf{Operation} \\\hline
    F & - & Fetch instructions\\\hline
    D & 0 & \makecell[l]{Read general-purpose registers AR and QR\\Decode instructions, detect interlocks, and forward operands}\\\hline
    E & 1 & \makecell[l]{For arithmetic instructions, run the ALU (add, subtract, multiply, and so on)\\For loads, generate the virtual address\\For branches, select the target address}\\\hline
    M & 2 & Issue memory reads and writes \\\hline
    W & 3 & Write results and loaded data back to registers\\\hline
\end{longtable}

An instruction can enter the pipeline only when its operands and required hardware resources are ready. In practice, the following hazards can stall the pipeline and delay instruction issue.

\subsection{Data Hazard}
If instruction A writes register X (an explicit general-purpose register or an implicit special register) and instruction B reads the same register, then B depends on A. If A produces the value at the end of stage SA and B needs it at the start of stage SB, A must be issued $D = max(SA - SB + 1, 0)$ cycles before B.\\
If B is fetched fewer than $D$ cycles after A, the processor delays issuing B until $D$ cycles have elapsed. That delay is called an interlock.\\
For example, if SA for A is W and SB for B is E, then $D = max(2 - 1 + 1, 0) = 2$, as shown in Figure \ref{fig:pie_data_hazard}.\\
When a result becomes available at the end of a stage, dependent instructions normally wait until it is written to a register. The processor also supports bypass (forwarding): it can forward a value from the producing stage to the consuming stage without waiting for write-back.

\begin{figure}[H]
    \centering
    \fbox{\includegraphics[width=0.9\textwidth]{\modulefiles/figures/data_hazard__EN}}
    \caption{Interlock Caused by Operand Dependency}
    \label{fig:pie_data_hazard}
\end{figure}

Data dependencies depend on which operands each instruction uses and at which stages they are read or written. Section \ref{sec:pie-instruction-descrip} lists the use and def stages for each instruction operand. 


\subsection{Hardware Resource Hazard}
If multiple instructions need the same hardware resource in the same cycle, only one may use it and the others are delayed. For example, the processor has eight 16-bit multipliers. If instruction C needs all eight in stage M and instruction D needs four in stage E, and C and D are issued in cycles T+0 and T+1 as in Figure \ref{fig:pie_resource_hazard}, both contend for four multipliers in cycle T+3. The processor then delays D by one cycle to avoid the conflict.

\begin{figure}[H]
    \centering
    \fbox{\includegraphics[width=0.9\textwidth]{\modulefiles/figures/resource_hazard__EN}}
    \caption{Hardware Resource Hazard}
    \label{fig:pie_resource_hazard}
\end{figure}

\subsection{Control Hazard}
Data and resource hazards can often be reduced by reordering code; control hazards are harder to hide. Conditional code becomes branch and jump instructions: if the condition is true, fetch continues from the target; otherwise sequential fetch continues. When a taken branch redirects fetch, as in Figure \ref{fig:pie_control_hazard}, instructions already in the F and D stages are discarded, which costs two pipeline cycles.\\

    \fbox{\includegraphics[width=0.9\textwidth]{\modulefiles/figures/control_hazard__EN}}
    \caption{Control Hazard}
    \label{fig:pie_control_hazard}
\end{figure}
